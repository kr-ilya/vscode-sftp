## После установки ничего не заливается

Так и задумано, и происходит это один раз.

Не имея записи о том, что лежит на сервере, SyncX не считает, что ваша локальная копия заведомо главнее. При первом запуске он запоминает состояние диска и принимает, что сервер ему соответствует, — чтобы устаревший локальный файл не затёр молча что-то живое.

Отправьте первую копию сами — **SyncX: Upload Project** или **Sync Local → Remote**, — и дальше изменения будут уходить самостоятельно.

## Почему моё изменение не залилось?

Событие на файле — повод проверить, а не повод отправить, поэтому файл, содержимое которого не изменилось, повторно не отправляется. Чтобы выяснить судьбу конкретного файла:

1. **SyncX: Show Change Detection Diagnostics** — сколько событий пришло и на какой ступени они остановились.
2. **SyncX: Dry Run: Show What Would Be Uploaded** — прогоняет весь конвейер и не передаёт ничего.
3. Канал вывода **SyncX: change detection** — по строке на событие, с причиной.

Обычные ответы: путь попадает под правило `ignore`; содержимое совпадает с тем, что было отправлено в прошлый раз; вотчер не настроен (`watcher.autoUpload` выключен и `uploadOnSave` выключен).

## Отказывается подключаться: host key изменился

Сервер, к которому вы уже подключались, предъявляет другой ключ. SyncX отказывает, а не спрашивает, потому что именно так выглядит man-in-the-middle.

Если смена ожидаема — сервер пересоздан или ключи ротированы, — удалите старую запись и подключитесь снова:

```sh
ssh-keygen -R example.com
```

Если ключ принимался через SyncX, а не через `ssh`, его собственное хранилище — файл `known_hosts` в каталоге global storage расширения; удалите строку для этого хоста там.

Если смены вы не ждали — не продолжайте, пока не выясните причину.

## Где хранится пароль?

В SecretStorage VS Code, а не в `.vscode/sftp.json`, — так что файл остаётся безопасным для коммита. Сохранить его предлагают только после того, как он действительно сработал.

- **SyncX: Forget Saved Password** удаляет его.
- Переставший работать пароль сбрасывается автоматически, и вас спрашивают заново.
- Пароль, вписанный прямо в конфигурацию, по-прежнему работает и используется как есть; в этом случае ничего не сохраняется.

## Просит подтвердить назначение

Один раз на каждое назначение, перед первой передачей в него, вместе со списком того, что в этом каталоге уже лежит.

Опечатка в `remotePath` не видна в конфигурации — это совершенно обычный путь, просто не ваш, — а делает её необратимой именно первая заливка. Список, начинающийся с `bin, boot, dev, etc`, объясняет положение дел лучше любого предупреждения.

**SyncX: Reset Confirmed Upload Destinations** заставит спросить снова.

## Всё заливается дважды

В одном воркспейсе включены и SyncX, и оригинальное расширение. Команды, представления и настройки у них разные, но `.vscode/sftp.json` они читают **один и тот же** — и оба реагируют на каждое сохранение.

Отключите одно из них для этой папки: вкладка Extensions → расширение → *Disable (Workspace)*.

## Error: Failure

Общее сообщение от сервера: SFTP-сервер отвечает так, когда системный вызов не удался, а сказать что-то более определённое ему нечего. Обычно причину показывает включённое на стороне сервера отладочное логирование и повтор передачи.

Две вещи стоит попробовать первыми:

- Если `remotePath` указывает на символическую ссылку, используйте путь, в который она разрешается.
- У сервера могли закончиться файловые дескрипторы. Поднимите его лимит, если можете; если нет — включите в конфигурации [`limitOpenFilesOnRemote`](docs/configuration.md#limitopenfilesonremote), который держит количество одновременно открытых хендлов под ограничением.

> Если вы это уже пробовали раньше: в расширении, из которого сделан форк, включение `limitOpenFilesOnRemote` бросало исключение при подключении, и соединение просто не устанавливалось. Здесь оно работает.

## Error: Connection closed

Старые серверы могут не поддерживать алгоритмы, которые согласуются по умолчанию. Задайте их явно в `.vscode/sftp.json` — этот список убирает `diffie-hellman-group-exchange-sha256`, который и оказывается виновником чаще всего:

```json
{
  "algorithms": {
    "kex": [
      "ecdh-sha2-nistp256",
      "ecdh-sha2-nistp384",
      "ecdh-sha2-nistp521"
    ],
    "cipher": [
      "aes128-gcm",
      "aes128-gcm@openssh.com",
      "aes256-gcm",
      "aes256-gcm@openssh.com",
      "aes128-cbc",
      "aes192-cbc",
      "aes256-cbc",
      "aes128-ctr",
      "aes192-ctr",
      "aes256-ctr"
    ],
    "serverHostKey": [
      "ssh-rsa",
      "ssh-dss",
      "ssh-ed25519",
      "ecdsa-sha2-nistp256",
      "ecdsa-sha2-nistp384",
      "ecdsa-sha2-nistp521",
      "rsa-sha2-256",
      "rsa-sha2-512"
    ],
    "hmac": [
      "hmac-sha2-256",
      "hmac-sha2-512"
    ]
  }
}
```

Сужение `serverHostKey` меняет то, какой ключ предложит сервер, поэтому следующее подключение может спросить про ключ, которого вы раньше не видели. Это ожидаемо — сверьте отпечаток с выводом `ssh-keygen -lf`, прежде чем принимать.

## ENFILE: file table overflow

macOS довольно жёстко ограничивает число открытых файлов. Поднимите лимит:

```sh
echo kern.maxfiles=65536 | sudo tee -a /etc/sysctl.conf
echo kern.maxfilesperproc=65536 | sudo tee -a /etc/sysctl.conf
sudo sysctl -w kern.maxfiles=65536
sudo sysctl -w kern.maxfilesperproc=65536
ulimit -n 65536
```

Снижение `concurrency` в конфигурации уменьшает число одновременных передач — помогает по той же причине.

## `passive: false` игнорируется

FTP-транспорт — `basic-ftp`, активного режима у него нет, поэтому параметр сопровождается предупреждением и используется пассивный режим.

Активный режим требует, чтобы сервер открыл соединение обратно к вашей машине, чего почти не допускает ни один файрвол или NAT, — поэтому пассивный и является умолчанием десятилетиями.

## Как залить содержимое папки, а не саму папку?

Укажите папку в `context`. Всё, что под ней, станет корнем синхронизируемого дерева.

Так JavaScript и HTML из `./build` попадут прямо в `/folder1/folder2/folder3`, без каталога `build` на сервере:

```json
{
  "name": "My Server",
  "host": "example.com",
  "protocol": "sftp",
  "port": 22,
  "username": "user1",
  "remotePath": "/folder1/folder2/folder3",
  "context": "./build",
  "uploadOnSave": false,
  "watcher": {
    "files": "*.{js,html}",
    "autoUpload": true,
    "autoDelete": false
  }
}
```

## Как заливать от root?

Никак — и никакой параметр конфигурации этого не даёт.

> В других источниках встречается совет прописать `"sshCustomParams": "sudo su -;"`. Для передач он не делает ничего: этот параметр дописывается к командной строке команды **Open SSH in Terminal** и к SFTP отношения не имеет.

В самом SFTP нет механизма смены пользователя посреди сессии; сделать это честно — значит запустить на сервере оболочку и протолкнуть файл через неё, а это отдельная функциональность со своими последствиями для безопасности. Здесь она сознательно не реализована.

Что делать вместо этого:

- Дайте учётной записи, под которой подключаетесь, право записи в целевой каталог — сменить владельца через `chown` или добавить её в группу, которой запись разрешена.
- Заливайте в каталог, куда писать можно, а перенос на место делайте отдельным привилегированным шагом на сервере.

## Как держать обе стороны в согласии автоматически

Заливать по мере изменений и повторять удаления:

```json
{
  "name": "My Server",
  "host": "example.com",
  "protocol": "sftp",
  "port": 22,
  "username": "user1",
  "remotePath": "/folder1/folder2/folder3",
  "uploadOnSave": false,
  "watcher": {
    "files": "**/*",
    "autoUpload": true,
    "autoDelete": true
  },
  "syncOption": {
    "delete": true
  }
}
```

Когда вотчер покрывает `**/*`, ставьте `uploadOnSave` в `false`, иначе сохранённый файл попадёт в очередь дважды.

С git это тоже работает: переключение ветки или откат изменений подтягивает сервер следом — причём отправляется только то, что действительно различается.

> **`autoDelete` удаляет на сервере.** VS Code сворачивает удаление папки в одно событие, поэтому одно событие может означать рекурсивное удаление. Именно поэтому он выключен по умолчанию. Сначала поживите с `"autoUpload": true, "autoDelete": false` и посмотрите в канал **SyncX: change detection**, что именно было бы удалено.

## В дереве сервера не видно скрытых файлов

По FTP решение о том, показывать ли dot-файлы, принимает сервер.

**proftpd** — отредактируйте `proftpd.conf`, он лежит в одном из мест:

- `/etc/proftpd.conf`
- `/etc/proftpd/proftpd.conf`
- `/usr/local/etc/proftpd.conf`
- `/usr/local/etc/proftpd/proftpd.conf`

Замените `ListOptions` с `"-l"` на `"-la"`:

```conf
<Global>
[...]
ListOptions "-la"
[...]
</Global>
```

По SFTP скрытые файлы перечисляются как обычно. Если там чего-то не хватает, проверьте `remoteExplorer.filesExclude` в конфигурации — по умолчанию скрываются `.git`, `.svn`, `.hg`, `CVS` и `.DS_Store`.
